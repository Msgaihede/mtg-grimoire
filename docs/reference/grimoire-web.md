# Grimoire Web (WASM & Worker Host)

`crates/grimoire-web` compiles `grimoire-core` to WebAssembly (`wasm32-unknown-unknown`) and runs it
inside a dedicated Web Worker on the browser, communicating with the UI via the `Core` seam.

The design is [the light-app spec](../superpowers/specs/2026-10-01-light-app-android-and-web-design.md) §6;
the build, benchmark, and deploy records are in [light-app.md](light-app.md) §9.

---

## The Exported Contract

The Web Worker exposes three functions through `wasm-bindgen`:

| Export | Arguments | Return Shape | Notes |
| :--- | :--- | :--- | :--- |
| `open(directory)` | OPFS directory name (string) | JSON: `{"kind":"ready", ...}`, `{"kind":"already-open"}`, or `{"kind":"failed","message":"…"}` | Opens the SQLite OPFS pool for the given directory. |
| `call(name, args, body?)` | Command name, JSON args string (`"null"` for none), optional `Uint8Array` | JSON: `{"ok": <value>}` or `{"err": "<sentence>"}` | Dispatches to `grimoire_core::dispatch`. Never throws. |
| `listen(handler)` | Callback: `(name, payload)` | None | Registers event forwarder. A subsequent call replaces the previous handler. |

### TypeScript Mirror Invariant
- The declarations in `src/lib/core/web/grimoire_web.d.ts` and the parser in `protocol.ts` mirror `wire.rs` by hand.
- Because `dist-wasm/` is ignored by Git, declaration files generated by `wasm-bindgen` do not exist in clean checkouts.
- **Rule**: Any change to an export signature in `wire.rs` must update `grimoire_web.d.ts` and `protocol.ts` in the **same commit**.
- `scripts/build-wasm.mjs` verifies that all three export names exist in the compiled artifact.

## Invariant: Nothing May Trap or Reject

A panic or unhandled trap in a Web Worker **does not** arrive as a rejected promise on the page. It lands in the Worker's `onerror` handler with no actionable context, causing the UI to hang indefinitely.

To prevent silent hangs:
1. **Errors Are Values**: Every failure mode (`open` errors, invalid JSON args, missing commands, failed database queries) is captured and returned as an `{"err": "..."}` or `{"kind":"failed", ...}` payload.
2. **Panic Hook**: A custom panic hook is installed on initialization to write panic sentences to `console.warn` / `console.error` before exiting.
3. **No Uncaught Rejections**: Rust promises never reject uncaught.

## OPFS Pool Handling & Worker Lifecycle

1. **`already-open` vs `failed`**:
   - Access to SQLite files in Origin Private File System (OPFS) uses exclusive synchronous access handles.
   - If another Worker holds the handle, opening fails with `DOMException`.
   - The code specifically detects `DOMException.name === 'NoModificationAllowedError'` anywhere in the error text to return `already-open`. All other exceptions return `failed`.
2. **Worker Outliving Document**:
   - In Chromium browsers, a Web Worker performing synchronous work can outlive its owning page by 1–3 seconds during page reloads or navigations.
   - The frontend uses the Web Locks API (`src/lib/core/web/holder.ts`) to distinguish between a stale lingering Worker from a previous reload and an active second browser tab.

## Single-Threaded Event Loop & Cooperative Yielding

Because WASM runs in a single-threaded Web Worker:
- **Shared Event Loop**: CPU work, network downloads, and `call()` message handlers run on the same thread.
- **Cooperative Yielding (`yield_to_host`)**:
  - Long operations (such as bulk Scryfall downloads, tag processing, and combo ingestion) must periodically yield execution back to the browser event loop.
  - The engine calls `grimoire_core::platform::timer::yield_to_host` every 50ms of CPU work.
  - Without this yield, UI status polls (`sync_status`) would be blocked for 10–30+ seconds.
- **No Locks Across `.await`**:
  - `Mutex` or `RefCell` borrows must **never** be held across an `.await` boundary in WASM.
  - Re-entering the event loop while holding a borrow results in a panic or deadlocks.
- **Live sync shares that loop** (phase 6, step 6.3):
  - `host::live_sync` — the core's `sync_engine::live::run` — is spawned beside the launch's downloads, over the Worker's own `WebSocket` (`platform::socket`'s browser arm). The socket's events are tasks on this event loop; the loop's reads and round trips run where they stand, on the one connection.
  - Measured in headless Chrome 154: the Worker is busy about 5 ms a minute idle, in a group or not, and a `search_cards` beside a round trip waits at most one of the trip's stretches (7–11 ms). See [light-app.md](light-app.md) §10.3.
